# BlockCraft Ukraine

Україномовна платформа спільноти Minecraft: знайти моди, зборки, скіни, сервери → зберегти в обране й колекції → поділитися своїм. Курсова робота + проєкт для портфоліо. Розробник один, працює 2–3 години на день.

- Повна технічна специфікація й етапи: `docs/tech.md` (не читай цілком — лише розділ поточного етапу й довідкові розділи, на які він посилається).
- Поточний стан і журнал рішень: `docs/PROGRESS.md` — читай на початку кожної задачі.

## Мова
- Зі мною спілкуйся українською.
- Код, імена, коміти, коментарі в коді — англійською.
- Усі тексти інтерфейсу — українською (в одному місці на сторінку/фічу, щоб потім легко додати i18n).

## Стек
- Бекенд: Python 3.13, Django 5.2 LTS + DRF, django-allauth (headless), Celery + beat, PostgreSQL 17, Redis 7, Meilisearch, uv.
- Фронтенд: Next.js 16 (App Router) + React 19 + TypeScript strict, Tailwind CSS 4, TanStack Query 5, openapi-fetch, react-hook-form + zod, next-themes, motion, skinview3d, pnpm.
- Інфраструктура: Docker Compose, Nginx (один origin для фронтенду й API), GitHub Actions, VPS.

## Команди
Усе запускається через `make` з кореня репозиторію:
- `make up` / `make down` / `make logs` — підняти / зупинити / логи (сайт на http://localhost:8080)
- `make migrate`, `make makemigrations`
- `make test` (усе), `make test-back`, `make test-front`
- `make lint`, `make fmt`, `make typecheck`
- `make api-types` — перегенерувати `frontend/src/lib/api/schema.d.ts` після будь-якої зміни API
- `make sync-mods`, `make seed`
- Одиночний тест бекенду: `docker compose exec backend uv run pytest apps/mods/tests/test_api.py -k download`

## Структура
- `backend/apps/<name>/` — Django-застосунки за шаблоном: `models → services (запис) → selectors (читання) → serializers → views (тонкі)`; зовнішні API — у `clients.py`, фонові задачі — у `tasks.py`, тести — у `tests/`.
- `backend/apps/core/kinds.py` — реєстр типів контенту (`mod`, `skin`, `server`, `collection`, …) для обраного, лайків, відгуків, коментарів, скарг. Нові типи контенту реєструй тут.
- `frontend/src/components/ui/` — примітиви дизайн-системи; `frontend/src/features/<name>/` — компоненти розділів; `frontend/src/app/` — маршрути.
- `docs/` — специфікація, прогрес, матеріали курсової.

## Як працюємо
1. Одна задача з `docs/PROGRESS.md` за раз. Не починай наступний етап, доки поточний не відповідає «Готово, коли» з `tech.md`.
2. Для задачі, що зачіпає більше 3 файлів або змінює моделі чи API, спершу покажи короткий план (файли, моделі, ендпоінти, тести) і дочекайся мого «ок».
3. Порядок реалізації: моделі + міграції → сервіси й тести → API + тести → `make api-types` → фронтенд.
4. Після реалізації запусти `/check` і виправ усе, що впало.
5. Онови `docs/PROGRESS.md`: відміть задачу; якщо відійшов від `tech.md` — запиши рішення в «Журнал рішень» і онови `tech.md` у тому ж коміті.
6. Коміти робить лише `/commit` після мого підтвердження. Ніколи не роби `git push` сам.
7. Якщо не впевнений щодо продуктового рішення — запитай, а не вигадуй.

## Визначення готовності задачі
- Тести на нову логіку є й проходять; `make lint` і `make typecheck` чисті.
- Міграції створено й застосовуються з нуля.
- API описано в OpenAPI (серіалізатори й `extend_schema` де потрібно), типи фронтенду перегенеровано.
- UI перевірено в обох темах і на ширині 375 px; є стани завантаження, порожньо й помилки.
- `docs/PROGRESS.md` оновлено.

## Правила коду — бекенд
- Бізнес-логіка лише в `services.py`; views і serializers її не містять.
- Лічильники (`likes_count`, `favorites_count`, …) змінюй лише через сервіси з `F()` у транзакції.
- Зовнішні API (Modrinth, Mojang, сервери) викликаються лише з `clients.py` і лише в Celery-задачах або з кешем; у тестах — тільки моки (`respx`, monkeypatch).
- Будь-який список у API — без N+1: `select_related` / `prefetch_related` / анотації; у тестах списків використовуй `django_assert_max_num_queries`.
- Права доступу — DRF permission-класи; приватні колекції й закриті профілі перевіряй у selectors.
- Секрети лише з оточення. Не читай і не виводь вміст `.env`.

## Правила коду — фронтенд
- Типи API лише з `schema.d.ts`; руками DTO не пиши.
- Кольори, відступи, шрифти — лише через токени з `src/styles/tokens.css`; жодних hex у компонентах.
- Дизайн: редакційний мінімалізм — великі заголовки із засічками, багато повітря, кути без заокруглень, рамки 1 px, без тіней і градієнтів, одна головна дія на екран, мінімум тексту. Перед роботою з UI завантаж skill `design-system`.
- 3D (skinview3d) — лише для скінів; завантажуй через `dynamic(..., { ssr: false })`.
- Каталоги й сторінки об'єктів рендеряться на сервері; мутації — через TanStack Query з оптимістичним оновленням.

## Чого не робити
- Не додавай нові залежності без пояснення, навіщо вони й чому не вистачає наявних.
- Не перезаливай файли модів на наш сервер — лише посилання на Modrinth.
- Не додавай приватні повідомлення між користувачами (безпека юних гравців).
- Не використовуй офіційні логотипи й текстури Minecraft; ілюстрації — власні.
- Не змінюй згенерований `schema.d.ts` і застосовані міграції руками.
- Не вимикай тести й лінтери, щоб «пройшло».

## Корисні skills і агенти
- `/next-stage` — взяти й виконати наступну задачу з PROGRESS.md.
- `/check` — усі лінтери, типи й тести.
- `/commit` — коміт у форматі Conventional Commits.
- `design-system` — правила UI (завантажується автоматично при роботі з фронтендом).
- Агент `code-reviewer` — незалежне рев'ю наприкінці етапу.
