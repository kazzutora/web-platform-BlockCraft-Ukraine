# BlockCraft Ukraine (v2)

Україномовний навігатор по контенту Minecraft: Java Edition. Контент — моди, ресурспаки, шейдери, датапаки, модпаки, сервери, скіни — береться з відкритих джерел (Modrinth, MineSkin, Mojang). Ми додаємо: підбір під «Мою гру» (версія + лоадер), перевірку сумісності й залежностей, збірки з експортом у `.mrpack`, переклади й відгуки українською. Шлях гравця: **знайти → взяти → поділитися**. Курсова робота + портфоліо; розробник один, працює 2–3 години на день.

## Що читати
- `docs/product.md` — навіщо, для кого, сценарії С1–С7. На початку кожного етапу.
- `docs/tech.md` — як будувати. Не цілком: розділ поточного етапу (13) і довідкові розділи, на які він посилається.
- `docs/PROGRESS.md` — стан і журнал рішень. На початку кожної задачі.
- `docs/sources.md` — факти про зовнішні API (поля, ліміти, умови). Перед будь-якою роботою з джерелом.
- `docs/archive/v1/` — перша версія. Лише довідка, не джерело вимог.

## Мова
- Зі мною — українською.
- Код, імена, коміти, коментарі в коді — англійською.
- Тексти інтерфейсу — українською, в одному місці на фічу (`features/<name>/copy.ts`); апостроф — `’`.

## Стек
- Бекенд: Python 3.13, Django 5.2 LTS + DRF, django-allauth (headless), Celery + beat, PostgreSQL 17, Redis 7, Meilisearch, httpx, pydantic, mcstatus, Pillow, uv.
- Фронтенд: Next.js 16 (App Router, Cache Components) + React 19 + TypeScript strict, Tailwind CSS 4, TanStack Query 5, openapi-fetch, react-hook-form + zod, next-themes, radix-ui, pixelarticons, skinview3d, pnpm.
- Інфраструктура: Docker Compose, Nginx (один origin), GitHub Actions, VPS.

## Команди
Усе — через `make` з кореня:
- `make up` / `make down` / `make logs` — сайт на http://localhost:8080 (`make up-local` + `pnpm dev` — фронтенд на Windows локально)
- `make migrate`, `make makemigrations`
- `make test`, `make test-back`, `make test-front`, `make lint`, `make fmt`, `make typecheck`
- `make api-types` — після будь-якої зміни API
- `make sync` (усі джерела) / `make sync s=modrinth` — синхронізація; `make seed` — демо-гравці поверх реальних даних (лише dev)
- Один тест: `docker compose exec backend uv run pytest apps/compat/tests/test_resolver.py -k cycle`

## Структура
- `backend/apps/<name>/`: `models → services (запис) → selectors (читання) → serializers → views (тонкі)`; дані з джерел — `importers.py`; задачі — `tasks.py`; тести — `tests/`.
- `backend/apps/sources/clients/` — **єдине** місце для HTTP до зовнішніх API; фікстури реальних відповідей — `apps/sources/tests/fixtures/<source>/`.
- `backend/apps/compat/` — двигун сумісності: чисті функції, без HTTP і без запису в БД.
- `backend/apps/core/kinds.py` — реєстр типів контенту (`mod`, `pack`, `server`, `skin`, `collection`).
- `frontend/src/components/ui/` — примітиви; `frontend/src/features/<name>/` — розділи; `frontend/src/app/` — маршрути.

## Як працюємо
1. Одна задача з `docs/PROGRESS.md` за раз. Наступний етап — лише коли поточний відповідає «Готово, коли».
2. Задача на > 3 файли або зі зміною моделей / API — спершу короткий план (файли, моделі, ендпоінти, тести, що побачу в UI), чекай мого «ок».
3. Порядок: моделі + міграції → сервіси / importers + тести → API + тести → `make api-types` → фронтенд.
4. Нове джерело чи нове поле джерела — спершу фікстура реальної відповіді, потім код.
5. `/check` після реалізації; виправ усе, що впало.
6. `docs/PROGRESS.md`: відміть задачу; відхилення від `tech.md` — у «Журнал рішень» і правка `tech.md` у тому ж коміті.
7. Наприкінці етапу — **продуктова перевірка**: пройди сценарії з `product.md`, які зачіпає етап, зніми скріншоти 375 і 1440 px, коротко опиши, що побачить гість: навіщо сторінка, що взяти, що опублікувати. Покажи мені.
8. Коміти — лише `/commit` після мого підтвердження. `git push` сам не роби.
9. Продуктове рішення, якого немає в документах, — питай, не вигадуй. Специфікація суперечить реальному API чи коду — скажи й запропонуй рішення, не підганяй.

## Визначення готовності задачі
- Тести на нову логіку є й проходять; `make lint` і `make typecheck` чисті.
- Міграції застосовуються з нуля; видалення моделей — окремою міграцією.
- API описано в OpenAPI, типи фронтенду перегенеровано.
- Контент у UI показує джерело (`SourceBadge`); головна дія сторінки — `TakeButton`.
- UI перевірено в обох темах і на 375 px; є стани завантаження, порожньо, помилка.
- `docs/PROGRESS.md` оновлено.

## Правила — джерела контенту
- Кожен об'єкт каталогу має `source`, `external_id`, `external_url` (міксин `Sourced`) і показує джерело.
- HTTP до зовнішніх API — лише через `apps/sources/clients/`, лише з Celery-задач або з кешем у Redis; кожна синхронізація пише `SyncRun` через `sync_run(...)`.
- Назви полів зовнішніх API — з фікстур, не з пам'яті. Немає фікстури — спершу запиши її (R1.2).
- **Не вигадуй контент:** ні демо-серверів, ні демо-модів, ні фейкових скінів чи відгуків від «реальних» людей. `make seed` — лише демо-гравці та їхні дії поверх синхронізованих даних, лише dev.
- Файли модів і модпаків не зберігаємо — лише посилання на CDN джерела. Кешуємо лише текстури скінів 64×64, прев'ю й обкладинки-мозаїки.
- Файлів від гравців не приймаємо. `/import` отримує лише хеші й `modrinth.index.json`, які дістає браузер.
- Не парсимо HTML сайтів без відкритого API (NameMC, Planet Minecraft тощо).

## Правила коду — бекенд
- Бізнес-логіка — лише в `services.py` / `importers.py`; views і serializers її не містять.
- Лічильники — лише через `core.counters.bump()` (`F()` у транзакції).
- Списки — без N+1 (`select_related` / `prefetch_related` / анотації); тести списків — `django_assert_max_num_queries`.
- Права — DRF permission-класи; приватне (чернетки збірок, приватні добірки, `share_token`) — у selectors.
- Задачі Celery ідемпотентні, приймають id, великі обсяги — пачками.
- Секрети — лише з оточення. Не читай і не виводь вміст `.env`.

## Правила коду — фронтенд
- Типи API — лише з `schema.d.ts`; руками DTO не пиши.
- Кольори, відступи, шрифти — лише токени з `src/styles/tokens.css`; жодних hex у компонентах.
- Дизайн — редакційний мінімалізм (skill `design-system`): заголовки Unbounded, текст Inter, версії й IP — JetBrains Mono, багато повітря, кути 0, рамки 1 px, без тіней і градієнтів, одна головна дія на екран.
- «Моя гра» — `getGameContext()` у Server Components, `GameChip` у шапці; фільтри каталогів за замовчуванням — з неї, перемикач «усі версії» — у URL.
- Тексти пояснень сумісності — `features/compat/copy.ts` за кодами з API.
- 3D (skinview3d) — лише для скінів, через `dynamic(..., { ssr: false })`.
- Каталоги й сторінки — SSR; мутації — TanStack Query з оптимістичним оновленням і відкатом.

## Чого не робити
- Не додавай залежності без пояснення в журналі рішень (навіщо й чому не вистачає наявних).
- Не повертай видалене у v2 (лайки, коментарі, завантаження скінів, моменти, рівні, стрічку) без мого рішення.
- Не додавай особисті повідомлення між гравцями.
- Не використовуй офіційні логотипи й текстури Minecraft; ілюстрації — власні.
- Не змінюй згенерований `schema.d.ts` і застосовані міграції руками.
- Не вимикай тести й лінтери, щоб «пройшло».
- Не чіпай VPS без мене (там працює інший проєкт).
