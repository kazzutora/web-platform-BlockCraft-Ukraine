# Бекенд (Django + DRF)

- Структура застосунку: `models.py` (лише поля й Meta) → `services.py` (усі зміни стану, транзакції) → `selectors.py` (складне читання) → `serializers.py` → `views.py` (тонкі ViewSet-и) → `urls.py`. Дані з джерел мапить у моделі `importers.py` (upsert за `(source, external_id)`, ідемпотентно).
- Сервіси — функції з ключовими аргументами: `def add_favorite(*, user: User, kind: str, obj_id: str) -> Favorite`. Помилки домену — `core.exceptions.DomainError(code=..., message=...)`, обробник перетворює їх у формат `{"detail","code","fields"}`.
- Типізуй сигнатури сервісів, селекторів, importers і клієнтів.
- Моделі контенту наслідують міксини з `apps/core/models.py` (`TimeStamped`, `Sourced` для всього з джерел, `Publishable` лише для створеного гравцями — збірки спільноти й переклади, `Engagement`) і реєструються в `apps/core/kinds.py`.
- Узагальнені зв'язки (обране, відгуки, скарги, переклади, «взяв») — через `content_type` + `object_id` з індексом і unique-обмеженнями.
- Лічильники — лише `core.counters.bump()` (`F()` у транзакції).
- Масиви версій / лоадерів — `ArrayField` з GIN-індексом.
- Фільтри каталогів — django-filter у `filters.py`; пагінація — класи з `apps/core/pagination.py`.
- Кожен новий ендпоінт: permission-клас, тротлінг-скоуп (якщо запис), `extend_schema` для нестандартних відповідей, тест на права й на успішний сценарій.
- Celery-задачі ідемпотентні, приймають id (не об'єкти), обробляють великі обсяги пачками.
- Тести: pytest-стиль, фабрики з `tests/factories.py`, `api_client` / `auth_client` фікстури з `conftest.py`.
- Міграції: одна логічна зміна — одна міграція; видалення моделей і полів — окремою міграцією; дані мігруй окремою `RunPython` з `reverse_code`.

## Джерела контенту

- HTTP до зовнішніх API — **лише** в `apps/sources/clients/` (httpx з таймаутом, повторами, паузою на 429, pydantic-схемами відповіді) і лише з Celery-задач або з кешем у Redis; ніколи в запиті користувача без кешу.
- Назви полів джерела — з фікстур реальних відповідей у `apps/sources/tests/fixtures/<source>/` і з `docs/sources.md`, не з пам'яті й не з документації. Нового поля чи ендпоінта немає у фікстурі — спершу запиши фікстуру.
- Кожна синхронізація — у `with sync_run(source, job, params)`: лічильники created / updated / unchanged / skipped / failed і до 20 прикладів помилок.
- Тести клієнтів і importers — лише на записаних фікстурах (`respx`, monkeypatch для mcstatus); жодних живих запитів.
- Кожен об'єкт каталогу має `source`, `external_id`, `external_url`; у серіалізаторах контенту — `source: {name, url}`.
- Не вигадуй контент: жодних демо-модів, демо-серверів, згенерованих скінів чи відгуків від «реальних» людей. `seed` — лише демо-гравці та їхні дії поверх синхронізованих даних, лише dev.
- Файли модів і модпаків не зберігаємо — лише посилання на CDN джерела. Від гравців файлів не приймаємо.
- `apps/compat` — чисті функції: без HTTP і без запису в БД; відсутні проєкти повертає в `missing`, імпорт ставить викликач.
